# The AI-built app audit study — design

**Date:** 2026-09-17
**Goal:** $49 appwalk Desktop sales.
**Strategy:** earn attention with original research rather than promotion, using the
audit engine as the instrument. The study is the product demo.

## Why this and not an ad

appwalk's differentiated feature is the audit. The most reliable way to get a
technical audience to look at an audit tool is to publish an audit they care
about. "I scanned N AI-built apps and here is what I found" is a genre Hacker
News and r/programming reward, it is honest, and it produces one artifact that
every other channel can carry: the video, the Reddit posts, the npm README, the
Bluesky thread. Without it, a launch post is an ad and community presence is
repetition.

The report never pitches the tool. The tool is simply how the research was done.

## Sample frame

Public GitHub repositories carrying an identifiable AI-builder signature.
Measured 2026-09-17 via the authenticated Search API:

| Signature (README unless noted) | Public repos |
| --- | --- |
| `lovable.dev` | 288,047 |
| `"Built with Lovable"` | 37,809 |
| `bolt.new` | 8,279 |
| `"Generated by v0"` | 107 |
| `path:.bolt/prompt` | 1 |

`lovable.dev` at 288k is the headline figure in its own right. The `.bolt/prompt`
path query returning 1 shows path-based discovery is unreliable here; README
signatures are the workable axis. v0's 107 means v0 leaves almost no README
fingerprint — report it as a discovery limitation, do not present it as "v0 apps
are rare."

**Target sample:** ~1,000 repos, stratified across builders, randomly drawn
within each stratum. Pilot of 50 first to validate the pipeline end to end.

Rate limits available: 5,000 core requests/hour, 30 search requests/minute
(authenticated as `kevinpalencia46`, scopes `gist read:org repo workflow`).

## Method

For each sampled repo:

1. `git clone --depth 1 --single-branch` into a scratch directory.
2. Run `appwalk audit --json` against the clone.
3. Record the findings with provenance (builder stratum, repo size, stars, last
   push, default branch).
4. Delete the clone before moving to the next repo.

Findings land in a local JSONL store. Two views are derived from it: a
**notification view** holding plaintext repo identifiers, never published; and a
**publication view** in which the repo identifier is hashed and only aggregate
counts and masked snippets survive.

Shallow clones of a typical Lovable app run a few MB. At ~1,000 repos the
transient disk cost stays under 10 GB because clones are deleted as we go, and
the whole run is roughly two hours of Pi time. It is I/O-bound, not CPU-bound, so
it does not contend with the trading or scanner services for compute.

### The hard line

**We never test a discovered credential against its provider.** Not to confirm it
is live, not once, not "just to check." That is unauthorized access and it is the
difference between security research and intrusion.

Severity is therefore classified on **pattern confidence alone**. A committed
`sk_live_…` is high-severity because of what it is, not because we proved it
still works. Notifications say "this looks like a live Stripe key, please rotate
and verify" and leave verification to the person who owns it.

This constraint is a feature of the write-up, not an apology in it. State it in
the method section.

### Which findings trigger a notification

"Notify the worst" needs a threshold, or it becomes a judgement call made a
thousand times. **High severity** — and therefore notified — is a finding that
classified as a candidate real leak (not a fixture) AND whose `kind` is one of:

Verified against `src/audit/secrets.js` on 2026-09-17. The kinds the engine
actually emits are: `aws`, `db_url`, `env_in_git`, `generic_key`, `github`,
`google`, `private_key`, `slack`, `stripe_live`.

High severity is:

- `stripe_live` — live payment credentials
- `db_url` — a connection string carrying credentials
- `aws` — cloud provider keys
- `private_key` — any PEM/SSH private key
- `github` — a token that can write to the owner's repositories
- `env_in_git` — see the note below; in this study it is a strong signal

Everything else — `generic_key`, `google`, `slack` — is counted in the aggregate
and **not** emailed. Rationale: the six above can cost someone money or data
today; the rest are hygiene. Notifying on hygiene buries the signal and reads as
spam.

**`env_in_git` is stronger here than its name suggests.** The detector fires when
a `.env` file is present in the project tree, which in normal use can mean a
local untracked file. But we operate on fresh shallow clones, and a clone
contains only tracked files — so a `.env` we can see is a `.env` that was
committed. In this study it is a direct hit, not a warning.

### Known gap: no Supabase detection

`src/audit/secrets.js` has no pattern for Supabase keys — no `service_role`, no
`anon`, no bare JWT (`eyJ…`) shape. Confirmed by inspection, not assumed.

This is a problem for the study specifically, because Lovable is the dominant
stratum (288k repos) and Lovable apps are Supabase-backed by default. A leaked
`service_role` key bypasses row-level security entirely — it is the
highest-impact secret an app in this population can leak, and the scan as it
stands is blind to it. Publishing "here is what leaks in AI-built apps" while
unable to see the most consequential leak in the most common stack would be a
real methodological hole, and a reader would find it quickly.

It is also a straightforward product gap: appwalk's stated audience is
vibe-coders, the largest vibe-coding platform ships Supabase, and the tool does
not check for its credentials.

**Decision required before the scan runs.** Adding a `supabase` kind is a small,
well-bounded change to one detector plus its tests. The alternative is to state
the blind spot prominently in the report's limitations and under-count. The first
is better for both the study and the product; it does, however, mean this spec
touches the audit engine, which the original scope excluded.

### Noise handling

The audit flags test fixtures and documentation alongside real leaks — verified
by running it against appwalk's own repo, where it correctly surfaced the
deliberate `sk_l…cdef` fixtures in `test/audit-secrets.test.js` and the plan
document. Separating genuine leaks from fixtures is part of the method.

Classification rules, applied in order:
- Path contains `test/`, `tests/`, `__tests__/`, `fixtures/`, `spec/`, `docs/`,
  or `examples/` → candidate fixture.
- Snippet matches a known documentation placeholder shape (`sk_live_abc…`,
  `xxx`, `your-key-here`, repeated characters) → fixture.
- Everything else → candidate real leak.

**The false-positive rate is itself a finding and gets published.** A tool that
claims zero false positives on this corpus would be lying, and the audience
checks.

## Deliverables

1. **The report page.** A standalone page built for a technical audience: method,
   sample construction, findings, masked examples, and limitations stated plainly
   in their own section. Its own URL, not a storefront path — Hacker News reads a
   vendor domain as an ad.
2. **The disclosure round.** Emails to maintainers of high-severity findings,
   sent *before* publication. Aggregate-only in the report; nothing identifiable,
   ever.
3. **The video.** Showrunner, Kevin's own voice, screen recording only, no face.
   appwalk pointed at one genuinely messy AI-built app, start to finish.
4. **The dataset.** Aggregate and anonymized, downloadable. Costs nothing and
   buys most of the credibility.

## macOS prerequisite

`appwalk-app` currently builds `win` and `linux` targets only; there is no `mac`
block in its electron-builder config. The free CLI runs fine on macOS (zero
dependencies, plain Node), so driving Mac traffic without a Mac build sends the
most likely buyers to a dead end at the purchase step.

The 2015 Intel MacBook Air (`MacBookAir7,1`, 4 GB, `shinigami@100.70.64.1`) can
produce an x64 target and cross-build arm64. It is 4 GB and not fast; expect the
build to be slow and to need care about disk.

**Gatekeeper:** an unsigned, un-notarized app shows "cannot be opened because the
developer cannot be verified" on first launch. Signing and notarization require
an Apple Developer account at $99 USD/yr. This is a Kevin decision and is
deliberately *not* a blocker on the build itself — an unsigned build plus clear
install instructions ships, and signing can follow.

## Components

Each is independently testable and has one job.

| Unit | Does | Depends on |
| --- | --- | --- |
| `corpus.js` | Builds and persists the sample: runs the signature queries, strata, random draw, writes `corpus.jsonl` | GitHub Search API |
| `harness.js` | Clone → audit → record → delete, one repo at a time, resumable | `corpus.jsonl`, appwalk audit |
| `classify.js` | Fixture-vs-leak rules, severity assignment | findings store |
| `aggregate.js` | Publication view: hashing, counts, the dataset export | findings store, `classify.js` |
| `notify.js` | Disclosure list and mail merge from the notification view | findings store, `classify.js` |

The harness must be resumable: a run over 1,000 network-bound clones will be
interrupted, and restarting from zero each time is not acceptable. It records
per-repo completion so a restart skips finished work.

## Testing

- `corpus.js`: stratification and draw are deterministic under a seed; API
  responses mocked.
- `harness.js`: clone/audit/delete against local fixture repos, including a repo
  that fails to clone and one that times out — neither may abort the run.
- `classify.js`: table-driven over known fixture paths and known real-leak
  shapes. This is the unit that decides what gets published, so it gets the most
  tests.
- `aggregate.js`: no plaintext repo identifier survives into the publication
  view. Assert this explicitly — it is the privacy guarantee.
- `notify.js`: never emits a raw credential; renders masked snippets only.

## Error handling

Network failures, private-gone-public repos, oversized repos, and clone timeouts
are all expected at this sample size. Each is recorded as a per-repo outcome and
the run continues. A repo that cannot be processed appears in the published
method as sample attrition with its reason — silently dropping failures would
misstate the denominator.

Disk is guarded: the harness refuses to start below a free-space floor and
deletes each clone before the next.

## Limitations to state in the report

- README signatures find repos that *declare* their builder; apps that removed
  the signature are invisible. The sample is of self-identified AI-built repos.
- Public repos are not representative of all AI-built apps. Most are never
  published, and the ones that are may skew toward learning projects.
- Pattern-matched secrets are not verified live. Some findings will be dead keys.
- The false-positive rate is measured and reported, not assumed away.

## How this decomposes into plans

This spec is larger than one implementation plan. It splits cleanly at the seams
below, and each piece is independently shippable:

1. **macOS build** — `appwalk-app` only. No dependency on the study; can run in
   parallel with everything else. Smallest piece.
2. **The scanner** — `corpus.js`, `harness.js`, `classify.js`, plus the pilot.
   This is the bulk of the engineering and where the tests concentrate.
3. **The outputs** — `aggregate.js`, `notify.js`, the report page, the dataset.
   Blocked on a completed run.
4. **The launch** — video and channel posts. Blocked on the report, and mostly
   Kevin's own work rather than mine.

Write plan 1 and plan 2 first; 3 and 4 are drafted once the pilot tells us what
the data actually looks like.

## Out of scope

Marketplace-style distribution, paid acquisition, Product Hunt, and a macOS
signing certificate are all deliberately excluded from this spec. Changes to
appwalk's audit engine are excluded **with one exception**: the Supabase detector
described above, if approved. Every other audit behaviour is used exactly as
shipped, which is the point.
